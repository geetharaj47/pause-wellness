# MindTrace Project Rules

This document outlines the strict guidelines governing code quality, safety boundaries, privacy protections, research integrity, and git workflows for the MindTrace project. All development must strictly adhere to these rules.

---

## 1. Safety Boundaries (Non-negotiable)
*   **No Clinical Claims:** The code must never use words like "depression", "anxiety", "PTSD", "bipolar", "clinical", or "diagnose" in user-facing UI text or explanations.
*   **Permissible Vocabulary:** Use low-risk wellness terms, e.g., "wellness pattern", "shift in normal pattern", "stress signals", "academic pressure", "sleep factors".
*   **Framing Suggestions:** Suggestive, reflective, and non-prescriptive framing only. Ask questions rather than making claims: "Does your workload feel more demanding than usual?" instead of "Your workload is causing your stress."
*   **Zero AI-Doctoring:** The system must never claim to replace professional psychological counseling, psychiatrists, or medical treatment.
*   **Crisis Safety Overlay:** If critical crisis keywords are matched, intercept the user immediately. Do not generate a AI reflection; instead, present local crisis helplines and options to reach out to a trusted contact.

---

## 2. Privacy-by-Design Rules
*   **Zero Raw Journal Logs:** Raw journal text must *never* be printed to standard output, application logs, console logs, or error monitoring frameworks.
*   **DB Column Protections:** Raw journal text columns must be isolated and, where feasible, encrypted at rest. Derived numeric signals (e.g., stress score = 0.45) can be stored unencrypted for mathematical analysis.
*   **No Data Sharing:** There must be no third-party analytic services (like Google Analytics or Hotjar) tracking journal text or user activity.
*   **Anonymized Researcher Dashboard:** The administrator/researcher dashboard must only load aggregated tables (e.g., overall precision/recall/F1). Querying or displaying individual journal strings in the researcher dashboard is strictly forbidden.

---

## 3. Code Quality & Architecture
*   **Strict Typing:** Use Python type hints on the backend (FastAPI, Pydantic, SQLModel) and TypeScript/ESLint rules where feasible on the frontend.
*   **Secrets Management:** Never commit API keys, database credentials, or secret keys to Git. Use environment variables managed via a `.env` file, and provide a `.env.example` file.
*   **No Giant Monolithic Files:** Break components into logical modules:
    *   Backend: split into `auth`, `journal`, `nlp`, `models`, `database`, and `schemas`.
    *   Frontend: split into components (cards, charts, layouts) and pages (login, dashboard, entry).
*   **Validation:** All API endpoints must enforce payload validation using Pydantic schemas. Catch database and model errors gracefully and return generic, user-safe error messages.
*   **Code Documentation:** Maintain documentation inline using docstrings for complex logic. Do not remove existing documentation or comments.

---

## 4. Git & Commit Guidelines
*   **Semantic Commits:** Use prefix tags in commit messages to clearly organize changes:
    *   `feat:` (new features)
    *   `fix:` (bug fixes)
    *   `docs:` (documentation changes)
    *   `style:` (formatting, missing semi-colons, etc.)
    *   `refactor:` (code restructuring without changing features)
    *   `test:` (adding or refactoring tests)
    *   `research:` (experiments, data simulation, statistical plotting)
*   **Granular Commits:** Commit often and avoid large, monolithic commits containing multiple unrelated features.

---

## 5. Research Integrity & Validation
*   **Zero Fake ML:** Never mock research results, model precision/recall, anomaly scores, or baseline tests in final evaluation. Every result must be programmatically generated by running real model scripts.
*   **Simulation Labeling:** During initial development and UI demonstration, any dummy data must be clearly labeled as `SIMULATED / DEMONSTRATION DATA`.
*   **Temporal Splits:** When partitioning longitudinal data for evaluations, strictly enforce temporal ordering (e.g., training on days 1–30, testing on days 31–45). Never shuffle time-series data or allow future journal entries to influence past predictions.
